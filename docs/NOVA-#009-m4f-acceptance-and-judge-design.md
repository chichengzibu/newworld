## 一、为什么做这件事

### 1.1 M4-E 的成功信号还是弱代理

M4-E 的评分器判的是「**过程**有没有出错」（工具调用全成功 / 有最终答复 / 结构约束满足）。
它衡量的是过程，不是「**用户满不满意**」。

而技能值不值得留，最终是用户说了算。

### 1.2 业界把用户反馈当最硬的信号

经典的 trace-to-eval 路径：**用户点踩 → 该 trace 进评测集 → 下次改动对着真实失败回归**。
用户反馈不是辅助指标，是主指标。

### 1.3 但「成功」信号的第四层（LLM 裁判）也不能是主指标

M4-E 留了 `llm_judge` 的接口没实现。原因是业界对 LLM 裁判的共识很硬：

- **judge drift 真实存在**：换裁判模型、换提示词顺序、换评分描述，结果都会变
- 裁判**偏爱长答案**、对自己的输出有偏好
- 推荐配比是「~30% 启发式 + ~10% 参考答案 + **~40% pairwise 裁判** + ~20% 人工」
- 且**只对 2~5% 的流量跑裁判**（够统计置信度就行）

所以本批把裁判实现为**可选第四层**：进综合分与说明，**不改 pass/fail**。

## 二、实现

### 2.1 用户接受度（`electron/learning/AcceptanceLog.ts`）

| 信号 | 判定 | 强度 |
|---|---|---|
| 用户点了「重新生成」 | `rejected` | **最强** —— 用户主动花一次 token 换答案 |
| 下一条消息**以纠正词开头** | `rejected` | 中 |
| 下一条消息**以认可词开头** | `accepted` | 中 |
| 都没命中 | `unknown` | — |

**为什么只认「句首」的词**（关键设计）：

「不是」「不对」在**正常任务描述**里也常见 ——
「把**不是**苹果的挑出来」「**不对**称的那些别动」。
若全文匹配，大量正常后续指令会被误判成「不满意」，
而误判的代价是**让效用统计偏悲观** —— 比没有统计更糟。

**为什么「用户没再说话」不算满意**：那可能只是用户走开了。
宁可少判，不要让效用统计偏乐观。`unknown` 占多数是正常状态。

**分母口径**：接受率的分母只算**有明确信号的**（accepted + rejected），
`unknown` 不进分母 —— 否则「用户根本没用这个技能」看起来像「用户不满意」。

### 2.2 采集链路

```
ChatManager.recordAgentOutcome 后
  → AcceptanceLog.registerRun({conversationId, messageId, skills, category})
      ↑ 先登记:用户信号是**事后**才有的(看到答复才可能点重新生成)
渲染层
  → 下一条消息发出前:查上一条助手消息 → classifyAcceptance(text) → 有信号才上报
  → 点「重新生成」:直接上报 rejected
```

### 2.3 LLM 裁判层（`electron/learning/RunJudge.ts`）

```ts
type RunJudge = (run, expectation) => Promise<JudgeVerdict>
```

- **可注入** → 单测里注入假裁判，不联网；生产里用本地 ollama 小模型
- **提示词按对比口径写**（pairwise 比绝对打分可靠），3~5 条明确标准 + 强制结构化输出
- **采样器确定性**（按序号取模，不用 `Math.random`）→ 同一批样本两次评估可比，可做回归
- **默认采样率 0.05**（业界建议的 2~5%）
- **解析容错**：允许 ```json 包裹、允许前后废话
- **`pass` 不是布尔 → 视为不可解析**（不当成 false —— 那是把不确定当成否定）
- **裁判不可用 ≠ 失败**：模型调用报错时记为「不确定」，不能算成质量问题

**裁判层不参与 pass/fail**：`judge drift` 真实存在，让它改结论就是让结论随裁判模型漂移。

## 四、遗留与后续

| # | 遗留 | 归属 | 说明 |
|---|---|---|---|
| 1 | **接受度只覆盖「重新生成」与句首关键词** | 已知边界 | 更细的信号（用户是否采纳建议、是否撤销文件操作）需要更多埋点 |
| 2 | **裁判层未接入生产路径** | 刻意 | `SkillTrial` 支持传 judge，但生产默认**不传** —— 采样率、模型漂移、额外成本都需要用户显式开启 |
| 3 | **裁判未做校准** | 后续 | 业界要求：先在人工标注样本上校准 judge 与人的一致度，再放量。本项目还没有人工标注集 |
| 4 | **接受度是「观察性」信号** | 口径 | 接受度来自真实使用 → 有混杂。它比「工具全成功」硬得多，但不是受控对照 |
| 5 | **对照实验里没有用户** | 口径 | 受控对照跑的是无人值守变体 → 接受度**不适用**。那一路只用确定性层 + 可选裁判 |
