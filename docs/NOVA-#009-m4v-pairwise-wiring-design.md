## 一、起因：用户要"接线"，但接线之前得先量

用户的原话是「做 M4-E 受控对照接 pairwise 裁判的接线」。M4-N 已经把"怎么接"
准备好了（换序双向 + 一致性要求），M4-N 设计文档的遗留 #1 写得很清楚：

> **pairwise 裁判默认不接** | D7 | 要接需要先解决 D7 的前提（裁判达标）。

所以接线之前有一个必须先回答的问题：**这个裁判接进来，产出的信号可信吗？**

M4-J 当时的结论是"两个本地模型都没达标"，但那是**单次顺序**口径。
M4-N 新增的「两次顺序一致才采信」这条规则**从来没被验证过** ——
它是一条**未经验证的代理**：顺序稳定 ⇒ 裁判在看内容 ⇒ 更可信。

不量就接 = 把一条未经验证的代理当事实用。

## 二、量出来的结论：这条规则是**反的**

复算入口：`tests/integration/judge-consensus-offline.test.ts`
（**不调模型** —— M4-J 的裁决已落盘成 `verdicts-<model>.jsonl`，纯计算秒级出结果）

| | qwen3.5:9b | qwen3.8-27b-q4km:latest |
|---|---|---|
| 计入样本 | 220 | 220 |
| 整体（单次顺序） | 一致率 70.9% · κ=0.411 | 一致率 71.8% · κ=0.467 |
| **顺序一致子集**（M4-N 采信的那个） | n=69 · 覆盖率 31% · 一致率 **44.9%** · κ=**−0.167** | n=52 · 覆盖率 24% · 一致率 **46.2%** · κ=**−0.003** |
| 顺序不一致子集（M4-N 记 unstable） | n=151 · 一致率 **82.8%** · κ=0.654 | n=168 · 一致率 **79.8%** · κ=0.610 |

**顺序一致的子集，κ 反而是负的。** 照 M4-N 的规则采信 =
**系统性地挑中裁判最不准的那批配对**，并且给它盖上"已验证"的名分。

### 2.1 那 82.8% 是**基准率假象**

把顺序不一致的子集按"裁判固定选哪个展示位"拆开：

| 组 | n | 组内一致率 | 组内多数类占比 | 组内 κ | 恒定预测？ |
|---|---|---|---|---|---|
| 两次都选先展示的 | 72 | 80.6% | 80.6% | **0.000** | **是** |
| 两次都选后展示的 | 79 | 84.8% | 84.8% | **0.000** | **是** |

裁判在这两组里**永远选同一个**，组内准确率**恰好等于**人工的多数类占比 ——
它"准"是因为**押中了多数类**，不是因为看懂了内容。
拼起来的 pooled κ=0.654 是**组间**差异（裁判选哪一组本身携带信息），
不是组内的判别力（组内 κ=0）。

### 2.2 裁判赢不了「只看长度」的平凡基线

拿一个**不看内容、只看答复有多长**的预测器（"永远选更长的那个"）同台比：

| | 值 |
|---|---|
| 基线「永远选更长的那个」 | 一致率 **82.1%** · κ=**0.638** |
| 裁判（qwen3.5:9b） | 一致率 70.9% · κ=**0.411** |
| 裁判与基线选择重合 | 70.2% |
| **人工标签 = 更长的那个** | **82.1%** |
| McNemar 独对数 | 裁判 21 : 基线 44 → **方向是裁判更差** |

**裁判比一个"数一下字数"的基线还差。** 更要紧的是最后一行：
**人工标注者自己就有 82.1% 选了更长的那个** ——
这份标注集被长度偏好主导，**无法区分**"裁判看懂了内容"与"裁判在押注长度"。

### 2.3 结论

现有两个本地裁判模型**没有可用的质量信号**。
在此基础上把它们接进生产，等于给受控对照加一个**看起来专业、实则更差**的参考列。

## 三、那怎么交付"接线"？

不是"把它接上"，而是**把它接成一个会被门禁拦住的东西**：

1. **测量可复现** —— 两项新指标进校准层，随报告一起出，随门禁一起判。
2. **门禁真拦人** —— D7 从注释变成代码：没达标 = 裁判**一次都不被调用**。
3. **接线真接了** —— 生产路径真的能跑裁判（此前 `ChatManager.runSkillUtilityTrial`
   **从不传 judge**，裁判在生产上一次都没跑过，M4-N 只活在单测里）。
4. **不达标说得清** —— 界面写明**具体哪一项**不达标，不是笼统的"不可用"。

## 四、做法

### 4.1 测量层（`electron/learning/JudgeCalibration.ts`）

| 新增 | 回答什么 |
|---|---|
| `consensusAnalysis()` | 「两次顺序一致才采信」买到了什么？拆两个子集，各报 n/覆盖率/一致率/κ/CI/多数类占比；再把位置偏置子集拆成组，报**组内 κ** 与**是否恒定预测** |
| `lengthBiasBaseline()` | 裁判强于「永远选更长的那个」吗？基线 κ / 裁判 κ / 选择重合 / 人工偏长率 / McNemar 独对数 |

两项都进 `CalibrationReport` 与 `renderCalibrationReport`，并进"可信"判定。

**方向性检验**：McNemar 必须分方向。实跑踩到 —— 裁判独对 21 : 基线独对 44，
双侧 p=0.0064（差异显著）但**方向是裁判更差**；拿双侧 p 当"裁判更强"的判据
会得出完全相反的结论。故新增 `mcnemarPValueOneSided()`：b ≤ c 直接判"没有优势"。

**不可测 ≠ 不达标**：两侧等长 → 基线不可测。此时**不拦门禁**
（否则一份测不出基线的标注集会否掉一个干净的裁判），但报告写明「不可测」；
组内人工标签单一类别时 κ 无定义，此时 κ 记 0 并标 `kappaDefined=false` ——
不让 `1` 冒充"完美一致"。

### 4.2 门禁层（`electron/learning/JudgeTrust.ts` + `JudgeCalibrationRecords.ts`）

**六项全中才放行**：

| # | 条件 | 不达标的后果 |
|---|---|---|
| 1 | 有归档校准记录，模型标识**完全一致** | 换模型即失效（judge drift） |
| 2 | n ≥ 30 | 样本太小 → 结论不成立 |
| 3 | κ ≥ 0.6 | 原始一致率会骗人（标签偏斜） |
| 4 | 换序改口率 ≤ 10% | 位置偏置超标 |
| 5 | 冗长相关性 ±0.2 | 长度偏好主导 |
| 6 | 「顺序一致才采信」规则在该模型上成立 | 否则采信 = 系统性挑错 |
| 7 | 裁判显著强于长度平凡基线 | 否则测到的可能只是长度 |

**记录为什么进仓**（而不是放 userData）：进仓 = **可审计** ——
谁在什么时候、用哪个模型、量到什么数、结论是什么，都在 git 历史里。
一条"看起来达标"的记录必须有人为它负责 —— 进仓才有这个人。

现有两条记录（两个模型，均**未达标**）也留着：
门禁读到它们能给出**具体哪一项不达标**，而不是一句"没有记录"。

### 4.3 接线层

| 层 | 改动 |
|---|---|
| `SkillTrial.ts` | `TrialOptions.pairwiseGate`：传了 judge 却没凭据（或凭据不放行）→ **不跑**，并在 `summary.judgeStatus` 写明原因 |
| `ChatManager.ts` | `runSkillUtilityTrial(skillId, tasks, { enableJudge })`：按**用户当前启用的 provider** 查门禁；`getJudgeTrust()` 供界面查 |
| `IpcServer.ts` | `skills:runUtilityTrial` 透传 `enableJudge`；新增 `skills:judgeTrust` |
| `preload.ts` | 暴露 `skills.judgeTrust`、透传 `enableJudge` |
| `SkillsView.vue` | 勾选框在门禁不通过时**禁用**并写明原因；结果里 `judgeStatus` **独立渲染** |

**为什么裁判用「用户配置的模型」而不是写死的裁判模型**：
校准记录按模型归档 —— 换模型 = 旧记录失效。
写死模型会让门禁查一个跟实际调用不同的模型 → 放行形同虚设。

**为什么不跑而不是"跑了再说"**：一次 pairwise 判定是**两次模型调用**。
对没校准过的裁判花这个钱，换回的结论既不能用、又会污染说明。
