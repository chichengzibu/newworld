# NOVA #008 — M4-C 模式证据链（提案凭什么成立）

> **状态**：已实现（2026-10-27）
> **对应台账**：DEV-055 ~ DEV-059
> **分支**：`feat/harness-wiring`
> **前置**：[M4-A 技能系统渐进披露](NOVA-#008-m4-skill-progressive-disclosure-design.md) · [M4-B 学习闭环接线](NOVA-#008-m4b-learning-closure-design.md)

## 一、为什么做这件事

### 1.1 M4-B 留下的最后一环

M4-B 把学习闭环的**数据层**接通：轨迹捕获、结果追踪、诊断反馈、效果反馈。
但闭环的最后一环 ——「从观察里提炼出技能」—— 仍是旧实现，而且旧实现的产出**不可信**。

### 1.2 旧 Reflector 的三个问题

旧实现（`SelfLearner.buildAnalysisPrompt` + `generateSkillProposalFromAnalysis`）：

```
① 把最近 10 条观察的【指令文本】丢给模型,问"它们的共同模式是什么"
② 操作步骤 = 抄【最后一次】观察的 steps
```

| # | 问题 | 后果 |
|---|---|---|
| ① | 那 10 条可能**互不相关** | 模型只能强行编一个「共同模式」—— 幻觉的直接来源 |
| ② | 模型**拿不到任何执行证据** | 不知道跑了几次、成没成、做了哪些操作 → 「操作步骤」只能靠编 |
| ③ | 抄最后一次的步骤 | 含一次性动作；且 agent loop 的步骤形状 `{name, ok, durationMs}` 取不到 `description`/`type` → 每步都变成字符串 **`执行 undefined`** |

第 ③ 条是 M4-B 接线后暴露的：M4-B 让 agent loop 路径也开始记观察，
而它记的步骤形状与旧管道不同，旧提取函数直接崩成了 `执行 undefined`。

还有一个更隐蔽的：**提示词硬编码「连续执行了3个操作」，实际塞进去 10 条**。
提示词在跟模型撒谎。

### 1.3 为什么现在做

M4-B 让轨迹有了结构化的成败数据，M4-C 才有原料可归纳。
**顺序不能反**：先把数据接上，再改提炼方式，否则提炼出来的是空中楼阁。

## 二、设计依据（业界调研）

### 2.1 核心发现：瓶颈在生成与验证，不在存储

> 「自生成技能的平均收益接近零甚至为负 —— 模型无法可靠地编写它们受益于消费的程序性知识。
> 价值产生于**人工编辑**这一环。」
> —— Anthropic《Equipping agents for the real world with Agent Skills》

> 「distillation 步骤本身就是弱环所在，不是存储/检索机制的问题。」
> —— SkillsBench / AGENTS.md 论文的同一结论

**这直接决定了 M4-C 的形态**：不追求「让模型写出更好的技能」，
而是**让提案带上可核对的证据**，把判断权交回给人。

### 2.2 先选后归纳，不要让模型在无关样本里找规律

> ACE 明确点名两种失败模式：**brevity bias**（优化器塌缩成泛泛的短指令）
> 与 **context collapse**（模型每步重写上下文，把细节摘要掉）。
> —— ACE（arXiv:2510.04618，ICLR 2026）

推论：**不该把一堆可能互不相关的观察丢给模型让它"找共同点"**。
应当先在代码里聚类、选出证据达标的模式，再把**这一条模式的轨迹**交给模型归纳。

### 2.3 支持计数是最小可用信号

> 「support counts / helpful-harmful counters 是最小可用信号」
> —— ACE 与 ALTK-Evolve 两个独立工作收敛到同一条

推论：
- **支持度**（这条模式被观察到几次）作为**提案门槛**：1 次观察可能是偶然，
  拿偶然当模式做提案，正是「自生成技能收益为负」的来源之一
- **成功/失败计数**作为**质量门槛**：一直失败的模式不该被固化成技能

### 2.4 保留失败

> 「保留失败 —— 把事故转成评测用例，而不是让它们消失」

失败次数既进证据链（提案要诚实），也进提示词
（让模型知道这条流程**哪里容易坏**，技能描述里就能带上这个提醒）。

### 2.5 delta item 须带 provenance

> ACE 的 Reflector 产出的每个 delta item 都**标注来源轨迹 id**

推论：提案必须可回溯到具体执行 —— 用户能点开看「这技能是从哪几次执行来的」。

## 三、实现

### 3.1 顺序反转：先选，再归纳

```
旧:  最近 10 条观察 → 指令文本 → 模型 → "共同模式是什么?" → 抄最后一次的步骤

新:  最近 10 条观察 → 按归一化指令聚类 → 按支持度排序
                                              ↓
                              取第一个满足门槛的候选模式
                                              ↓
                          算证据链(支持度/成败/共同步骤/轨迹 id)
                                              ↓
                    把【这一条模式的轨迹证据】交给模型归纳
                                              ↓
                              提案 + 证据链 → 人来判断
```

### 3.2 门槛（两道，缺一不提）

| 门槛 | 常量 | 值 | 依据 |
|---|---|---|---|
| 支持度 | `MIN_SUPPORT` | ≥ 2 次 | §2.3 —— 1 次可能只是偶然 |
| 成功率 | `MIN_SUCCESS_RATE` | ≥ 50% | §2.3 —— 一直失败的模式不值得固化 |

**支持度不达标 → 根本不调 LLM**（省一次模型调用，也是对用户的尊重）。

### 3.3 分母口径（实现期踩坑并修正）

第一版把成功率算成 `successfulAttempts / supportCount` —— **分母混用**：

- `supportCount` = 这条模式**发生过几次**（含没有逐次证据的历史次数）
- `successfulAttempts` = **留有轨迹证据的那些次里**成功了几次（最多 5 次）

拿 3 ÷ 15 = 20% —— 成功率被系统性低估，于是提案永远出不来。
正确分母是**有逐次证据的运行数**（`successful + failed`）。
该缺陷由新测试捕获（`支持度达标 → 选中` 与 `分母口径` 两例）。

### 3.4 逐次轨迹（有界保留）

`Observation` 新增 `trajectories: TrajectorySummary[]`，每条观察保留**最近 5 次**执行的摘要：

| 字段 | 说明 |
|---|---|
| `ts` | 时间戳 |
| `trajectoryId` | 轨迹 id —— provenance |
| `outcome` | 逐次成败（不是聚合计数） |
| `steps` | 步骤摘要（**不含工具原始输出** —— 可能很大、可能含敏感数据） |
| `toolsUsed` | 用到的工具 |

**为什么有界 5 次**：桌面应用磁盘敏感。5 次足以归纳共同步骤，又不至于撑大 `observations.json`。

**为什么只存摘要**：学习数据只该留「做了什么、成了没成」，
不该把整段工具返回（可能含用户文件内容）写进学习库。

### 3.5 步骤摘要兼容多形状

不同来源的步骤结构不同，摘要函数统一处理：

| 来源 | 形状 |
|---|---|
| agent loop | `{ name, ok, durationMs }` |
| TaskExecutor | `{ type, description, status, error, startTime, endTime }` |
| 旧观察 | `{ type }` / `{ description }` |

摘要只保留 `name`/`type`/`description`/`ok`/`error` 五个可归纳字段；
**取不到名字的步骤直接丢弃**（编造「执行 undefined」比不写更糟）。

### 3.6 共同步骤归纳

**只保留出现在半数以上成功轨迹里的步骤** —— 剔除一次性动作
（某次顺手删了个临时文件，把它固化进技能反而是噪声）。
全部无交集时退回第一条成功轨迹的步骤（宁可给具体，不给空）。

### 3.7 证据链进提案、进 UI

`SkillProposal` 新增 `evidence`：

```ts
interface SkillEvidence {
  supportCount: number          // 观察到几次
  trajectoryIds: string[]        // provenance
  successfulAttempts: number    // 分母口径见 §3.3
  failedAttempts: number
  commonSteps: string[]
  toolsUsed: string[]
  sampleInstruction: string
}
```

`SkillsView.vue` 的提案详情弹窗新增「证据链」区块：
观察到 N 次 / 成功 N 次 / 失败 N 次 / 用到的工具 / 样例指令，
并明写口径 ——「支持度与成功率只是『值得学』的必要条件，不是『这个技能有用』的结论」。

### 3.8 提示词改写

| 旧 | 新 |
|---|---|
| 「以下是用户连续执行了3个操作」+ 10 条指令文本 | 证据摘要（支持度/成败/工具）+ **已归纳好的共同步骤** |
| 无 | 失败次数提醒（让模型提示用户哪里容易坏） |
| 无 | 明确要求「只依据上面的证据，不要编造证据里没有的操作」「描述要具体，不要泛化」 |
