# NOVA #009 — M4-O 小屏等比缩放（窄屏用户够不着发送按钮）

> **状态**：已实现（2026-11-13）
> **对应台账**：DEV-155
> **分支**：`feat/harness-wiring`
> **前置**：[M4-N 受控对照的结论增强](NOVA-#009-m4n-trial-signal-design.md)

## 一、问题

应用布局按 **1280px** 铺开：

```css
/* src/styles/global.scss */
#app { min-width: 1280px; }
```

而窗口又写死了 `minWidth: 1280`。两者叠加的后果：

| 屏幕 | CSS 宽度 | 窗口宽 | 结果 |
|---|---|---|---|
| 1920×1080 @100% | 1920 | 1280 | 正常（布局 1280 正好铺满窗口） |
| **1920×1080 @150%** | 1280 | 1280 | 正常（刚好） |
| **1366×768 @125%** | **1092** | 1280 | **窗口比屏幕宽 → 右边一截在屏幕外** |
| 1366×768 @100% | 1366 | 1280 | 正常 |

**1366×768 笔记本开 125% 缩放**是国内极常见的一档（Windows 默认 125%）。
那一档下：发送按钮、模型选择器、窗口控制按钮**全在屏幕外** → 用户点不到。

## 二、决策：等比缩放（用户 2026-11-13 拍板）

对比过三条路：

| 方案 | 代价 | 结论 |
|---|---|---|
| 改流式布局 | v4.4 的固定宽度设计整体重做（侧栏/面板/表格全要重排） | 太大，不是一批的事 |
| 降 `min-width` | 布局变成"能缩但难看"，右侧控件仍然错位 | 治标不治本 |
| **等比缩放** | 页面整体缩小，布局逻辑一行不改 | **采用** |

等比缩放是**固定宽度桌面应用的标准做法**（字号随之变小，可读性损失最小）。

## 三、做法

`electron/core/WindowManager.ts`：

1. **缩放系数** = `contentWidth / 1280`，上限 1（不放大）、下限 0.6（再窄就太小了，不如让用户横向滚）
   → `webContents.setZoomFactor(scale)`
   → **布局仍按 1280 铺开**（CSS 视口宽度回到 1280），只是整体变小 → **什么都不裁切**
2. **`minWidth` 1280 → 900**、`minHeight` 720 → 600
   —— 原来根本没法把窗口缩窄，缩放也就无从触发
3. **屏幕比设计宽度窄时，窗口占满屏幕宽度**（`min(1280, screenWidth)`）
   —— 窗口也不可能比屏幕宽，占满能让缩放系数更接近 1（更易读）
4. **resize 去抖 120ms** —— 拖动窗口时 resize 连续触发，每次都重排会卡
5. 缩放系数偏差 < 0.005 时不动 —— 避免无谓重排

## 四、实测

物理窗口 **1000×800**：

| 指标 | 值 |
|---|---|
| 缩放系数 | **0.78125**（= 1000/1280） |
| CSS 视口宽度 | **1280**（布局按设计宽度铺开，不是被裁） |
| 发送按钮 | 完整落在视口内、`elementFromPoint` 命中按钮自身/后代 → **点得到** |
| 截图 | 侧栏/会话列表/标题栏/输入区/发送按钮 **全部可见** |

回归用例：`tests/e2e/verification-small-screen.spec.ts`
（断的是「**缩放后还有没有东西被裁**」—— 后者才是用户真正遇到的故障，
而不是"缩放系数算对了"这种自嗨的断言）

## 五、遗留与后续

| # | 遗留 | 归属 | 说明 |
|---|---|---|---|
| 1 | 缩放后**字号变小** | 已知 | 1092 宽的屏上约 0.85 倍，字号偏小但可读。真要更好得改流式布局 |
| 2 | 缩放会放大**位图资源**的模糊度 | 已知 | 应用以 SVG 图标为主，影响小 |
| 3 | 下限 0.6 以下仍会裁 | 已知 | 900/1280 = 0.70 > 0.6，所以实际到不了下限；再窄的屏建议用更大的下限 |
| 4 | 未在**真实 1366×768 @125%** 机器上验 | 需设备 | 本机是 1920×1080，用 e2e 缩窗模拟（缩放逻辑与屏幕无关，行为等价） |
