> **分支**：`feat/harness-wiring`
> **前置**：[M4-E 受控对照](NOVA-#009-m4e-controlled-skill-validation-design.md) ·

## 一、起因：5 个配对就敢说"有帮助"

M4-E 的对照实验原本只做**比大小**：带技能成功率 80%、不带 40%，
差 40% > 门槛 10% → 判"有帮助"。

但那是在 **5 个配对任务**上得出的 —— 多对一次，差值就翻 20 个百分点。
而且当时**没有任何置信区间**，也没做显著性检验。

## 二、参照了哪些成熟实现、各取了什么

按项目惯例（新模块先对比高星高活跃实现再落地），这次横向看了三家：

| 参照 | 它怎么做 | 我们取了什么 |
|---|---|---|
| **inspect_ai**（UK AISI 的评测框架） | 每个指标都带 `stderr()` / `ci()`；二值用 `ci_wilson()`；另有 `bootstrap_stderr()`、聚类标准误；`ci()` 默认 Student-t，可切 bootstrap | **"结论必须带 CI"** 这条口径；二值用区间而不是单一差值；bootstrap 作为非正态数据的兜底 |
| **promptfoo 生态（Fullsend 的 `significance.py`）** | promptfoo 本身**不做显著性**（阈值只是通过率门槛），要外挂脚本算 Wilson / bootstrap；文档里有个经典案例：**19/20 = 95%，95% CI 是 [76.4%, 99.1%]，不通过 90% 门槛**；190/200 才通过 | **"同一致率、相反结论"** 这个警示 —— 直接推出"小样本不能只看点估计"；以及"按指标类型选检验" |
| **配对评测方法论（dd3ok 的配对评测总结）** | 二值用 **McNemar**；序数用 Wilcoxon / 符号检验；连续量用配对 t / 配对 bootstrap；报告效应量 + CI；盲测 + 换序 | **McNemar（二值）+ 配对 bootstrap（连续）** 的组合；"报效应量 + CI，不只报谁更高" |

**没取的**：
- 不引入它们的包（项目红线：**零新 npm 依赖**）——只复刻做法。
- 不做多重比较校正（FDR）—— 一次只评一个技能，没有"同时比较很多"的场景。
- 不做聚类标准误 —— 我们的样本没有分组结构。

## 三、做法（`electron/learning/TrialStatistics.ts`，零依赖）

| 函数 | 口径 | 为什么这么选 |
|---|---|---|
| `mcnemarExactP(b, c)` | **精确二项检验**（双侧），不是卡方近似 | 卡方近似在 `b+c` 很小时不准，而 5~10 个配对正是本项目常态 |
| `bootstrapMeanCI(values)` | 2000 次重采样，取 2.5%/97.5% 分位 | 配对差值是 {-1,0,+1} 的离散量，正态近似太糙 |
| `mulberry32(seed)` | 确定性伪随机 | **同批数据两次跑必须给同样的区间**，否则回归对比没意义（与 `RunJudge` 采样器同一取向） |
| `requiredPairsForDelta(b, c, 总对数)` | 按当前不一致比例外推，**用同一个精确检验**搜最小 n | 闭式功效公式在 Δ=1 时方差退化为 0，会算出"需要 0 个"这种荒唐结果 |
| `formatCI(ci)` | `[低, 高]` 百分比 | note 里直接展示 |

### 3.1 判定逻辑的变化（有意为之）

```
效应量过门槛(±10%) 且 McNemar p < 0.05  → positive / negative
效应量过门槛 但 p ≥ 0.05                → insufficient_data
                                           说明里写:方向、p 值、"约还需 N 对"
效应量不过门槛                           → neutral
n < 5                                   → insufficient_data
```

**关键数字**（本模块用用例钉住）：

| 不一致对 | McNemar 精确 p | 结论 |
|---|---|---|
| 5 胜 0 负 | **0.0625** | 不够 |
| 6 胜 0 负 | **0.03125** | 刚够 |

也就是说：**"5 个配对全对全错"依然不显著**。这正是原口径站不住的地方，
也是这次改动最实在的收获。

### 3.2 为什么"方向对但样本不够"不叫 neutral

`neutral` 的含义是"看不出差别"；而这里是"**看起来有差别，但数据还不足以支撑**"。
两者对用户的含义完全不同 —— 前者建议别再试，后者建议多跑几个任务。
故记 `insufficient_data`，并把方向与"还差多少"写进说明。

## 五、口径边界（写进代码注释）

- **频率派**近似，不是贝叶斯；不做多重比较校正（一次只看一个技能）。
- bootstrap **固定种子** —— 可复现，但换种子区间会有细微差别（2000 次重采样已足够稳定）。
- "还差多少对"是**按当前观察比例外推**的粗估：真实效应更小则需要更多。
- 检验的是**二值成功率的差**；综合分差的 CI 只作参考（它不参与判定，与 M4-N 口径一致）。

## 七、M4-AF 补：重复运行（epochs）

> 上面的遗留 #1：每个任务只跑一次，运行自身的随机性没被平均掉。

参照 **inspect_ai 的 epochs**（同一任务多轮采样 + 归约），补上：

| 项 | 做法 |
|---|---|
| 选项 | `TrialOptions.repeats`（默认 1；主进程封顶 5 —— 成本线性翻倍，不能让一次误输入烧光额度） |
| 二值归约 | **多数票**（`passed × 2 > 有效运行数`；平票按不通过 —— 保守） |
| 连续分归约 | **均值** |
| 点式裁判 | 只在**第一遍**上跑（裁判是一次模型调用，不能跟着重复数翻倍） |
| 部分重复失败 | 用成功的那几遍归约（实验故障 ≠ 任务失败）；全失败才作废该任务 |
| 会话隔离 | **每次运行开一个新会话、跑完即删** —— 之前整轮共用会话，重复跑会把上一轮的历史带进下一轮，模型能看到"刚才做过"，重复就失去意义 |

界面：技能验证卡片加「重复次数」（1~5），确认框里的总调用数按 `任务数 × 2 × 重复次数` 计算。

验证：`tests/unit/skill-trial-repeats-m4af.test.ts`（6 例）——
调用次数、缺省不重复、多数票通过 / 不通过、全失败作废、部分失败照常归约。

## 八、M4-AG 补：开跑前先算"要多少个任务"

> 遗留 #2：之前只能**跑完**才由数据反推"还差多少"；用户写任务时并不知道该写多少。

做法参照 **inspect_ai 生态的 evalconfidence** 与 **Fullsend 的 `significance.py`** ——
它们都把"最少试验数 / 功效"做成计算器。我们复刻的是配对二值比例的标准功效公式
（Connor 1987）：

```
n_d = (z_{1−α/2}·√t + z_{1−β}·√(t − Δ²))² / Δ²
n   = n_d / t
```

其中 Δ 是要检出的成功率差、t 是**假设的**不一致率（默认 0.4）。

| 要检出的差异 | 约需配对任务（80% 把握，t=0.4） |
|---|---|
| 50 个百分点 | 27 |
| 30 个百分点 | 82 |
| 20 个百分点 | 191 |

**这个结果本身就是个提醒**：想检出 20 个百分点的差异，需要近 200 个配对任务 ——
在桌面应用里这基本不现实。所以现实的做法是：
- 要么接受"只能检出很大的效应"（例如 6 个任务全对全错）；
- 要么把**重复运行**（M4-AF）用起来，用次数换稳定性。

**接线**：新增 IPC `skills:trialGuidance`，主进程按公式算好再给界面渲染
（不写死数字，算法与测试同一份）。技能验证卡片在任务输入框下方展示
"至少几个任务 / 检出 30%、20% 各约需多少"。

验证：`tests/unit/trial-statistics-m4ae.test.ts` +4 例（单调性 / 量级 / 边界 / 不一致率钳制）；
`tests/unit/skills-m4-panels.test.ts` +1 例（界面渲染主进程给的数字）。
