# NOVA #009 — M4-N 受控对照的结论增强：不再只有三档

> **状态**：已实现（2026-11-13）
> **对应台账**：DEV-152 ~ DEV-153
> **分支**：`feat/harness-wiring`
> **前置**：[M4-E 技能效用的受控对照](NOVA-#009-m4e-controlled-skill-validation-design.md) · [M4-J 裁判校准](NOVA-#009-m4j-judge-calibration-design.md)

## 一、为什么做这件事

M4-E 的受控对照回答「这个技能到底有没有用」。它的结论是三档：
`positive` / `negative` / `neutral`（或样本不足）。本批解决两个具体缺陷。

### 1.1 二元判定把信息扔了

`TaskGrader.GradeResult` 明明有 `score`（0~1 的分层均值：硬信号 / 结构约束 / 相似度），
但 M4-E 的对照**只用了 `passed` 这个二值**：

```ts
delta: (withGrade.passed ? 1 : 0) - (withoutGrade.passed ? 1 : 0)
```

后果：两次运行**都失败**时 —— 一次错 1 个工具、一次错 5 个 —— 二元差值一律记 0，
结论就是「看不出差别」。而这两次其实**差很多**。

M4-E 自己的注释就写着「3 次运行得出的差值一次翻转就是 ±33%」——
**二值信号在小样本下极其脆弱**。

### 1.2 「带/不带这个技能哪个更好」本来就是 pairwise 问题

业界一致：pointwise 分数会挤在高分区间、需要额外做量表校准；pairwise（哪一个更好）稳定得多。
而 M4-J 已经把 pairwise 裁判实现出来了 —— 但 M4-E 还在用「各自打分再比大小」。

## 二、做法

### 2.1 加连续信号，但**不动准入门**

- 每个配对任务新增 `scoreDelta`（带技能综合分 − 不带技能综合分）
- 汇总新增 `meanScoreDelta` 与 `scoreDeltaDirection`
  （`consistent_with` / `consistent_against` / `mixed` / `none`）
- **判定口径不变**：准入门仍用二元成功率差值（M4-E 设计已定：ACE 式准入门用 held-out reward，
  不用绝对成功率）。综合分差**只进说明**：
  二元结论是 neutral、但综合分差方向一致且 ≥ 门槛时，说明里补一句
  「但综合分有稳定差异（带技能高/低 N%）」—— 否则「看不出差别」会被读成「两者完全一样」。

### 2.2 pairwise 裁判路径（可选、默认关闭、且**强制换序双向**）

M4-J 实测：本地裁判的**换序改口率 68~80%** —— 单次顺序的比较几乎没有信息量。
所以：

| 做法 | 结果 |
|---|---|
| 正着跑一次（带,不带） | 只有一半信息，还带位置偏置 |
| **正反各跑一次，两次一致才采信** | 本批采用 |
| 两次不一致 | 记 `unstable`（**不是「平局」** —— 是「这个裁判在这一对上看不出稳定偏好」） |
| 裁判输出无法解析 | 记 `unstable`（`unknown` 不等于平局） |

且按 **D7**（裁判层保持默认关闭）：`pairwiseJudge` 不传就没有任何 pairwise 字段；
传了也**不参与 verdict**，只作为参考信号进说明 —— judge drift 真实存在，
不能让结论随裁判漂移。

### 2.3 界面

试验结果表新增两列：

| 列 | 内容 |
|---|---|
| **综合分差** | `+67%` / `-20%`，带符号配色 |
| **裁判对照** | 带技能更好 / 不带更好 / 平局 / 不稳定（没跑裁判时整列不出现） |

外加 `pairwise.note` **独立渲染**（不靠拼进 `summary.note`）——
「这个裁判顺序敏感」这类元信息藏起来等于没提示。

## 四、顺手修掉一个实测 8 轮红 1 轮的 flaky（DEV-153）

`tests/unit/Workspace.test.ts` 的排序断言偶发红。追下来**不是测试写错，是实现的契约没兑现**：

- `listWorkspaces` 承诺「按 createdAt desc（新的在前）」
- 但 `createdAt` 是 `Date.now()`（**毫秒精度**）→ 同一毫秒创建的两个 workspace 排序键相同
- 而 `Array.prototype.sort` 是**稳定**的（ES2019 起规范保证）→ 同键时保留插入顺序
  → 实际结果是「**旧的在前**」，与承诺相反

修法：`[...values()].reverse().sort((a, b) => b.createdAt - a.createdAt)` —— 先反转插入顺序
再稳定排序，「新的在前」在任何情况下都成立。**不用 id 做次级键**：id 是 `randomUUID().slice(0, 8)`，
随机、无序，带不出时间语义。

回归用例把 `Date.now` 钉成同一毫秒，让这个分支**每次都跑到**，而不是靠运气。
